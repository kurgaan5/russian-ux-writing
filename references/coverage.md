# Полное покрытие: review и write

Реестр [checks.json](checks.json) — единственный источник ID и критериев; [checks.md](checks.md) — его читаемое представление. 127 проверок относятся к разным уровням. Проверяй **все применимые пары «проверка × объект»**, а не один удобный пример каждого типа. Если формат отсутствует, соответствующий ID всё равно учитывается как неприменимый.

До заполнения строк учёта выполни [редактуру через разобранные примеры](example-led-editing.md): смысловой бриф, подходящее преобразование, реальные варианты и выбор. Реестр проверяет выбранную работу, а не заменяет её. Внутренние решения хранятся в editorial_decisions; готовый отчёт не начинается до этой работы и последующей проверки.

## 1. Сначала собрать доступный материал

До смысловой редактуры изучи все предоставленные материалы в пределах задачи: макеты целиком, читаемые тексты и изображения, соседние состояния, предыдущий и следующий шаги, имеющиеся пояснения пользователя, словарь и подключённую дизайн-систему. Если источник отсылает к существенному условию, проверь его доступный первоисточник. Не останавливай сбор на первом скриншоте или первых найденных ошибках.

В инвентаре веди список `materials`: `id`, `locator`, `status` (`read`, `unavailable`, `not_needed`), `reason` и `used_for`. Для недоступного источника укажи, что пробовал открыть и какая часть осталась непрочитанной. Для ненужного — конкретную причину неприменимости. Пользовательский текст в чате тоже может быть источником. Не обходи бесконечно весь интернет: нужен максимум **доступных и относящихся к задаче** свидетельств.

Если источник не прочитан полностью, не ставь `read` всему документу: раздели на прочитанную и недоступную части. Непрочитанный релевантный материал не заменяй догадкой. Пока ждёшь необязательное уточнение, продолжай независимые проверки; к завершению используй безопасное явно названное допущение. Недоступность источника должна отражаться и в тех проверках, которым не хватает свидетельств.

## 2. Инвентарь всех объектов

Сохрани рядом с результатом внутренний `inventory.json`:

- `mode`: `review` или `write`.
- `materials`: перечень источников и фактических результатов чтения.
- `units`: один объект `scope`, смысловые `block` и все отдельные `text`, включая хорошие тексты и динамические значения.
- Для каждого объекта: стабильный `id`, `kind`, `parent` (у scope — null), точный `locator`, `text`, `context`, дополнительные `tags`. В scope опиши границы и исключения, в block — роль, состояние и связи. Текстовый объект принадлежит блоку.
- В review `text` содержит исходник; предложенную замену храни в `candidate_text` того же объекта. В write `text` содержит окончательный текст; при редактуре можно сохранить `original_text`. Изменение текста, кандидата, контекста или тегов требует актуализации покрытия.
- Группировать можно только **дословно одинаковые** тексты с одинаковыми ролью и контекстом: `count`, все `locations`, `group_reason`. Разные суммы, даты и ID — отдельные значения; одну находку можно связать со всеми затронутыми объектами.
- Пустое место для нужного текста включи в инвентарь. В write заполни его, а не делай карточку об отсутствии текста.
- У строк задавай content_role: copy — авторская фраза, заголовок, подпись или команда; value — дата, время, сумма, номер или точный идентификатор. Для value укажи value_reason. По умолчанию используется copy, чтобы неверная разметка не снимала проверки молча. Обычное предложение с цифрами остаётся copy и при необходимости имеет тег data.

Дополнительные теги определяются функцией, а не именем слоя:

| Уровень | Теги |
|---|---|
| Текст | `button`, `link`, `data` |
| Блок / состояние | `list`, `input`, `tooltip`, `snackbar`, `informer`, `modal`, `onboarding`, `badge`, `empty`, `search`, `loading`, `success`, `error` |
| Канал / специальный формат | `push`, `sms`, `email`, `release`, `legal` |

Каждая строка получает проверки по kind=text, включая орфографию, формы при числах и регистр. Авторская речь дополнительно получает виртуальную область copy: ясность, тон и синтаксис фразы. Не нужно сочинять новые варианты «14:00» или оценивать эмоциональность номера; их данные, формат, типографика и компонент проверяются. Даты, суммы, время, единицы, контакты и идентификаторы дополнительно помечаются data. Ошибка ввода относится и к input, и к error; пустой поиск — к empty и search. Теги не наследуются автоматически: пометь нужные блоки и строки явно. Нельзя назвать предложение значением, чтобы исключить редактуру. Недоступная геометрия не делает FIT неприменимым.

## 3. Создать журнал и пройти проверки

Команды запускаются из папки скилла; файлы конкретной задачи храни в её выходной папке, не в пакете скилла:

```sh
python3 scripts/check_coverage.py init --inventory /absolute/task/inventory.json --coverage /absolute/task/coverage.json
python3 scripts/check_coverage.py validate --inventory /absolute/task/inventory.json --coverage /absolute/task/coverage.json
```

`init` создаёт строки для каждой подходящей пары, ничего не помечая пройденным. Для ID без подходящих объектов создаёт строку с unit_id=null и not_applicable. **Проверь полноту инвентаря и эту классификацию вручную.** Скрипт не видит пропущенную подпись на изображении и не понимает, что кнопка ошибочно размечена обычным текстом.

Работа идёт в порядке: контекст и факты → изучение подходящих примеров → структура и варианты блока → выбор формулировки → проверка реестром, грамотности и компонента → итоговое человеческое чтение. При написании сначала собери смысловую структуру и черновик по фактам. При необходимости возвращайся к предыдущему этапу. Не начинай с массового заполнения pass и не превращай проверку в защиту первого черновика.

Заполняй `rows` конкретным основанием `evidence`:

| Статус | Когда использовать |
|---|---|
| `pass` | Критерий проверен для указанного объекта; запиши наблюдение, сопоставление или источник |
| `finding` | Есть исправление или полезное улучшение; есть ID связанной находки |
| `not_applicable` | Нет формата или конкретного условия применения; укажи почему. Для обязательных проверок подходящего объекта этот исход запрещён |
| `unverified` | Проверка нужна, но факта, доступа, состояния или геометрии нет; укажи чего не хватает |
| `pending` | Только промежуточное состояние. В завершённом журнале запрещено |

Примеры оснований: «Кнопка открывает форму, поэтому “Оплатить” обещает преждевременный результат»; «Заголовок называет результат, подпись — подтверждённое место получения»; «Новая строка не подставлена, ширина компонента неизвестна». «Проверено», «Всё нормально», «Не нужно» или одна и та же заготовка во всех строках не являются редакторским свидетельством. Скрипт проверяет структуру, содержательность основания оценивает редактор.

Не выдавай общее наблюдение о странице за чтение отдельной строки. Приписывание исходной фразы к шаблонному выводу не делает его конкретным. Например, наличие обычного глагола в кнопке не подтверждает отсутствие канцелярита в соседнем пояснении. Для языкового pass назови проверенное сочетание или функцию именно этой строки; для решения о блоке прочитай весь блок. Если такого наблюдения ещё нет, проверка остаётся pending. Скрипт может разнести уже сделанные выводы по журналу; не генерируй им положительные языковые выводы из одного общего шаблона.

При `unverified` добавь соответствующую запись в `limitations`: check_id, unit_id, reason. Ограничение должно попасть в короткую заметку результата или относящуюся к нему карточку. Для нескольких одинаковых ограничений выдачу можно объединить. Полнота учёта не означает, что все пункты успешно проверены.

## 4. Находки и второй просмотр

В review `findings` — единственный реестр находок. Каждая запись:

- `id`, `type` (`fix` → «Исправить», `improve` → «Улучшить», `clarify` → «Уточнить»), `title`;
- `unit_ids`, `check_ids`, точный `before`, готовый `after` для правки, `why`;
- для clarify — `question`, без выдуманной готовой замены;
- при наличии — фрагмент, координаты, источник и статус проверки новой версии в компоненте.

В соответствующих rows заполни finding_ids; связи должны совпадать в обе стороны. Для вопроса о неизвестном факте используй unverified и свяжи уточнение. Исправление и улучшение оценивай раздельно: допустимую формулировку можно сделать яснее без объявления её ошибочной. Одно изменение, исправляющее несколько дефектов, связывается с несколькими check_ids; число карточек не равно числу проверок или затронутых мест.

В review статус строки относится к **исходному** объекту. Если новая конструкция устранила запятую или согласование, это всё ещё finding исходника, а не pass. Проверку качества замены запиши в evidence и passes.language. Общая карточка с типом fix может также улучшать ясность: перечисли все устранённые дефекты и привяжи соответствующие проверки. Не создавай отдельные конкурирующие замены одной строки ради каждого знака. После повторной проверки сверь прежние подтверждённые замечания с исходником и новым реестром; отсутствие старой находки требует основания, а не молчаливого исчезновения.

Перед завершением заново просмотри блоки и авторские строки **без связанных находок**, заполни `second_look[unit_id]`: что проверено ещё раз и почему исходник оставлен. Отдельно вернись к строкам, где уже есть только корректура: одна запятая не закрывает редактуру. Проверь вводное, повтор, тяжёлую конструкцию, неясный объект действия или информационный пробел. Если первый вариант оказался хуже, попробуй другой приём при тех же фактах. Если исходник хорош, сохрани его с конкретным основанием. Для value не нужна самостоятельная заметка о новой формулировке каждой цифры; проверки данных остаются обязательными. Минимального количества замечаний нет.

## 5. Особенности write

Напиши по фактам: что произошло / что предлагается → нужные условия → реальное действие. Выбирай приёмы из core.md по задаче, не превращай учебный шаблон в обязательную структуру.

Ошибки и полезные улучшения черновика **сразу внеси в текст** в пределах разрешённого редактирования. Повтори затронутые проверки, связку и полный финальный языковой проход. В итоговом coverage.json нет открытых findings. Если факта не хватает, сформулируй безопасно без неподтверждённого обещания; при необходимости кратко назови недостающий факт. Не дописывай значения, которых не знаешь.

Окончательный инвентарь должен содержать именно выдаваемую версию. Пересоздай журнал для неё и перенеси только те результаты, которые действительно остаются верны; затронутые пары проверь заново. Не обновляй хеш вручную ради прохождения проверки. Неизвестные свойства макета остаются unverified, даже если текст короткий.

**При создании текста отчёта вообще нет:** не строй PNG с замечаниями, мини-сайт, карточки «до/после» или таблицу самопроверки. Выполни разрешённую запись в целевой файл/макет либо отдай готовый текст по компонентам. Короткое существенное ограничение не является отчётом. Отдельное последующее поручение проверить написанное — новая задача в режиме review.

## 6. Условие перехода к отчёту или выдаче

Перед завершением заполни:

- `material_review`: какие доступные релевантные источники собраны, что осталось недоступным и почему дальнейший сбор сейчас не добавит свидетельств;
- `inventory_review`: сверка инвентаря с всей областью, полнота текстов, тегов и повторов;
- `passes`: конкретный итог каждого прохода context, relations, language, improvements, fit, human_reading. В language отрази вычитку исходника и выбранных замен в review; в write — окончательного текста после саморедактуры. В human_reading проверь смысл с позиции читателя без внутреннего брифа и естественность целых фраз;
- все пары rows, находки, второй просмотр и limitations.
- editorial_decisions по каждому блоку с авторским текстом: прочитанный пример, механизм, реальные варианты, выбранная версия и причина выбора; схема — в [методе работы](example-led-editing.md).

Запусти validate. Исправь пропущенные пары, незавершённые проходы, несвязанные находки и устаревшие снимки текста. Скрипт проверяет полный набор пар, основания, повторный просмотр, ограничения, режим и хеши инвентаря и реестра. **Он не доказывает качество редакторских решений и полноту исходного изображения.** Не заполняй массово pass ради зелёного результата.

**Отчёт разрешено начинать только после максимального сбора доступного релевантного материала, завершения всех применимых редакторских проверок и успешной проверки покрытия.** Не делай оформление параллельно незавершённому анализу. Начальная картинка с красной рамкой — согласование границ, а не отчёт с находками.

Если проверка объективно недоступна, завершённым считается её честный учёт как unverified с причиной после попытки получить данные. Нельзя писать «всё проверено» или «всё помещается». Если остались доступные непрочитанные материалы или выполнимые проверки, работа ещё не завершена. При недоступном Python сохрани тот же журнал и вручную проверь все пары; явно отметь, что автоматическая проверка не выполнялась, не сокращай редакторскую работу.

В review после этого читай [правила отчёта](review-output.md) и собирай артефакты из findings. В write выдавай готовый текст без отчёта. Внутренний журнал не публикуется по умолчанию.
